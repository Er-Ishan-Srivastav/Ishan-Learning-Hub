🌟 What is Apache Cassandra?

Understanding the distributed NoSQL database powering today's largest applications

🔍 Core Characteristics

Apache Cassandra is a distributed NoSQL database management system designed to handle large amounts of data across many commodity servers, providing high availability with no single point of failure.

📊

Wide Column Store

Data organized into rows and columns, but columns are flexible in number

🌐

Distributed Architecture

Data spread across multiple nodes with no central authority

🔄

High Availability

Continues to operate even when nodes fail

⚡

Elastic Scalability

Add or remove nodes without downtime

⚖️

Tunable Consistency

Choose between consistency and availability based on needs

🏗️

Column-family Model

Wide-column store data model for flexible schemas

📊 Perfect For:

  • Large amounts of unstructured or semi-structured data
  • Social media platforms and user activity tracking
  • Census data and government records
  • Financial transactions and trading systems
  • IoT sensor data and time-series applications
  • Content management and catalogs
📈

Horizontal Scalability

Add more nodes to your cluster to handle increased load. Linear performance improvement with each new node added.

🔄

High Availability

Designed to be highly available with no single point of failure. Continues operating even when multiple nodes fail.

⚡

High Performance

Handle high volumes of read and write operations simultaneously, perfect for real-time data processing applications.

🔧

Flexibility

Store various types of data formats, making it suitable for a wide range of use cases and applications.

🌐

Open Source

Completely open source, making it accessible and allowing users to customize and extend functionality.

Geographic Distribution

🏢 Cluster

  • A collection of many data centers
  • A cluster can have n number of data centers
  • Provides the highest level of fault tolerance and scalability
  • All data centers in a cluster share the same ring topology

🏭 Data Center

  • A logical set of racks (must contain at least one rack)
  • Used to provide fault tolerance, disaster recovery, and low latency access
  • Data centers are geographically distributed for better user experience
  • Replication Strategy replicates data across data centers for high availability

📦 Racks

  • A logical group of nodes within the ring
  • A collection of servers housed in the same physical location
  • Database uses racks to ensure replicas are distributed among different logical groups
  • Each machine in the rack has its own CPU, memory, and hard disk

🖥️ Nodes

  • A fully functional machine connected to other nodes with high network speeds
  • Can be physical servers, EC2 instances, or virtual machines
  • All nodes are organized in ring topology where every node works independently
  • Each node has the same role in the topology (peer-to-peer structure)

⚠️ Rack Failure Considerations

  • All machines in the rack are connected to the same network switch
  • All machines share a common power supply
  • A rack can fail due to network switch failure or power supply failure
  • If a rack fails, none of the machines on the rack can be accessed
  • All nodes on the rack will appear as down to the cluster

🗣️ Gossip Protocol - How Nodes Communicate

1 Gossip protocol initializing...
2 Node A sends gossip message to random nodes
3 Nodes exchange cluster state information
4 Failure detection and health monitoring
5 Cluster view converges across all nodes

🎯 How Gossip Protocol Works

Gossip Protocol is a peer-to-peer communication mechanism that ensures all nodes in a Cassandra cluster stay informed about each other's state.

  • Periodic Communication: Every second, each node initiates gossip with 1-3 other nodes
  • State Exchange: Nodes share information about themselves and other nodes they know
  • Failure Detection: If a node doesn't respond, it's marked as potentially down
  • Convergence: Eventually, all nodes have the same view of the cluster
  • Scalability: Works efficiently with thousands of nodes

🌱 Seed Nodes

Seed nodes are special nodes used to bootstrap new nodes into the cluster.

  • When a new node is added to the cluster, it needs to discover the topology
  • The new node connects to seed nodes to learn about other nodes
  • Seed nodes provide necessary information for the new node to join the cluster
  • This process is called bootstrapping
  • Seed nodes are critical for cluster initialization and new node discovery

🎯 Benefits of Gossip Protocol

  • Decentralized failure detection
  • Automatic cluster membership management
  • Network partition tolerance
  • Scalable to thousands of nodes
  • Self-healing cluster topology

📊 Data Partitioning - Hash Ring Distribution

📁 Partitioning.cql
-- How Cassandra determines data location CREATE TABLE users ( user_id UUID PRIMARY KEY, -- Partition key name TEXT, email TEXT ); -- Partition key gets hashed to determine node -- Hash function: Murmur3 -- Token range: -2^63 to 2^63-1 INSERT INTO users (user_id, name, email) VALUES (uuid(), 'John Doe', 'john@example.com'); -- Cassandra calculates: -- hash = murmur3(user_id) = 4567890123456789 -- node = find_node_for_token(4567890123456789)

🔧 How Data Partitioning Works

Data Partitioning distributes data evenly across all nodes in the cluster using consistent hashing.

  1. Hash Calculation: Partition key is hashed using Murmur3 algorithm
  2. Token Assignment: Hash value becomes a token (-2^63 to 2^63-1)
  3. Node Selection: Token determines which node stores the data
  4. Replica Placement: Replication factor determines additional copies
  5. Virtual Nodes: Each physical node handles multiple token ranges

🔄 Replication Strategy

🔄 SimpleStrategy

Use: Single datacenter only

Method: Places replicas on consecutive nodes clockwise

CREATE KEYSPACE simple_ks WITH replication = { 'class': 'SimpleStrategy', 'replication_factor': 3 };

🌐 NetworkTopologyStrategy

Use: Multiple datacenters (Production)

Method: Rack and datacenter aware placement

CREATE KEYSPACE prod_ks WITH replication = { 'class': 'NetworkTopologyStrategy', 'datacenter1': 3, 'datacenter2': 2 };

💾 LSM Storage Engine

📋 Commit Log

Sequential append-only log for durability

Speed: ~1ms write time

🧠 Memtable

In-memory sorted structure

Capacity: 512MB default

💿 SSTable

Immutable disk files

Compressed & Indexed

🔄 Compaction

Merge and optimize SSTables

Background process
1 Client sends write request to coordinator node
2 Write immediately recorded in commit log (durability)
3 Data added to memtable (in-memory performance)
4 Acknowledgment sent to client (write complete)
5 When memtable full, flush to SSTable on disk
6 Background compaction merges SSTables for optimization

🏗️ Data Modeling

Master the art of query-first data modeling for distributed systems

🏢 Cluster

The top-level container for all your data and nodes

  • Collection of multiple datacenters
  • Shares the same ring topology
  • Can span geographic regions

🗃️ Keyspace

Defines replication strategy and contains tables

CREATE KEYSPACE ecommerce WITH replication = { 'class': 'NetworkTopologyStrategy', 'datacenter1': 3, 'datacenter2': 2 };

📋 Table

Collection of rows with defined schema

CREATE TABLE products ( category TEXT, product_id UUID, name TEXT, price DECIMAL, PRIMARY KEY (category, product_id) );

📄 Row

Collection of columns identified by primary key

  • Must fit on a single node
  • Uniquely identified by primary key
  • Can have different column sets

🎯 Key Concepts to Remember

  • Keyspace: Similar to database schema in RDBMS
  • Table: Collection of rows, but more flexible than RDBMS
  • Row: Data unit identified by primary key
  • Column: Name-value pairs with timestamp and TTL

🎯 The Golden Rule: Query-First Design

Unlike relational databases, design your tables based on your queries, not normalized data structures.

❌ Traditional RDBMS Approach

  1. Normalize data to avoid duplication
  2. Create tables with foreign keys
  3. Write queries with JOINs
  4. Add indexes for performance

✅ Cassandra Approach

  1. Define your queries first
  2. Create one table per query pattern
  3. Denormalize data for performance
  4. Embrace data duplication

📊 Key Design Principles

  • Minimize Partition Access: Keep related data together
  • Avoid Large Partitions: Keep under 100MB per partition
  • Design for Your Queries: Each table answers specific questions
  • Denormalize for Performance: Storage is cheap, compute is expensive

🚫 CQL Limitations to Remember

  • No JOINs between tables
  • No subqueries or complex WHERE clauses
  • Limited aggregations (COUNT, SUM, etc.)
  • No GROUP BY/HAVING clauses
  • ORDER BY only on clustering columns
📁 PrimaryKeyExamples.cql
-- Simple primary key (single partition key) CREATE TABLE users ( user_id UUID PRIMARY KEY, name TEXT, email TEXT ); -- Composite primary key (partition key + clustering columns) CREATE TABLE user_posts ( user_id UUID, post_date DATE, post_time TIMESTAMP, content TEXT, PRIMARY KEY (user_id, post_date, post_time) ) WITH CLUSTERING ORDER BY (post_date DESC, post_time DESC); -- Compound partition key (multiple columns in partition key) CREATE TABLE analytics ( user_id UUID, event_type TEXT, timestamp TIMESTAMP, data MAP<TEXT, TEXT>, PRIMARY KEY ((user_id, event_type), timestamp) );

🔑 Partition Key

  • Determines which node stores the data
  • Used for horizontal distribution
  • Must be included in all queries
  • Should have high cardinality

🗂️ Clustering Columns

  • Determine sort order within partition
  • Enable range queries
  • Can be used in WHERE clauses
  • Define data retrieval patterns

🗃️ Keyspace Operations

-- Create keyspace for development CREATE KEYSPACE IF NOT EXISTS dev_app WITH replication = { 'class': 'SimpleStrategy', 'replication_factor': 1 }; -- Create keyspace for production CREATE KEYSPACE prod_app WITH replication = { 'class': 'NetworkTopologyStrategy', 'datacenter1': 3, 'datacenter2': 2 } AND durable_writes = true; -- Use keyspace USE prod_app; -- Alter keyspace replication ALTER KEYSPACE dev_app WITH replication = { 'class': 'SimpleStrategy', 'replication_factor': 3 };

📋 Table Operations

-- Create table with various data types CREATE TABLE IF NOT EXISTS users ( user_id UUID PRIMARY KEY, username TEXT, email TEXT, age INT, created_at TIMESTAMP, profile MAP<TEXT, TEXT>, interests SET<TEXT> ) WITH comment = 'User profiles table' AND gc_grace_seconds = 864000; -- Add column to existing table ALTER TABLE users ADD phone TEXT; -- Drop column from table ALTER TABLE users DROP phone; -- Create index for querying CREATE INDEX ON users (email); CREATE INDEX username_idx ON users (username);

✨ CREATE (INSERT)

-- Basic insert INSERT INTO users (user_id, username, email, created_at) VALUES (uuid(), 'johndoe', 'john@example.com', toTimestamp(now())); -- Insert with TTL (expires in 1 hour) INSERT INTO sessions (session_id, user_id, data) VALUES (uuid(), uuid(), 'session_data') USING TTL 3600; -- Conditional insert (only if not exists) INSERT INTO users (user_id, username, email) VALUES (uuid(), 'unique_user', 'unique@example.com') IF NOT EXISTS; -- Insert with collections INSERT INTO users (user_id, username, interests, profile) VALUES ( uuid(), 'alice', {'music', 'travel', 'technology'}, {'bio': 'Software Engineer', 'location': 'San Francisco'} );

📖 READ (SELECT)

-- Basic select SELECT * FROM users; SELECT username, email FROM users; -- Select with WHERE clause (must include partition key) SELECT * FROM users WHERE user_id = 123e4567-e89b-12d3-a456-426614174000; -- Select with LIMIT SELECT * FROM users LIMIT 10; -- Select with filtering (requires ALLOW FILTERING) SELECT * FROM users WHERE email = 'john@example.com' ALLOW FILTERING; -- Select with time range (clustering column) SELECT * FROM user_posts WHERE user_id = ? AND post_date >= '2024-01-01' AND post_date <= '2024-12-31'; -- Select with ORDER BY (only on clustering columns) SELECT * FROM user_posts WHERE user_id = ? ORDER BY post_date DESC;

📦 Batch Operations

-- Logged batch (ACID within single partition) BEGIN BATCH INSERT INTO users (user_id, username, email) VALUES (?, ?, ?); INSERT INTO user_posts (user_id, post_id, content) VALUES (?, ?, ?); UPDATE user_stats SET post_count = post_count + 1 WHERE user_id = ?; APPLY BATCH; -- Unlogged batch (better performance, no atomicity) BEGIN UNLOGGED BATCH INSERT INTO user_activity (user_id, activity_type, timestamp) VALUES (?, ?, ?); INSERT INTO activity_log (log_id, user_id, activity) VALUES (?, ?, ?); APPLY BATCH;

🔢 Counter Operations

-- Counter table (special table type) CREATE TABLE page_views ( page_id TEXT PRIMARY KEY, view_count COUNTER ); -- Increment counter UPDATE page_views SET view_count = view_count + 1 WHERE page_id = 'home'; -- Decrement counter UPDATE page_views SET view_count = view_count - 5 WHERE page_id = 'about'; -- Read counter SELECT page_id, view_count FROM page_views;

⚖️ Understanding Consistency in Cassandra

🎯 Consistency Levels

Level Read Write Latency Use Case
ANY N/A ≥1 (inc. hinted handoff) ~1ms Maximum availability
ONE 1 replica 1 replica ~2ms High performance
QUORUM Majority Majority ~15ms Production standard
ALL All replicas All replicas ~50ms Highest consistency
LOCAL_QUORUM Local majority Local majority ~10ms Multi-DC production

⚡ Lightweight Transactions (LWT)

-- Compare-and-set operations for strong consistency UPDATE users SET email = 'new@example.com' WHERE user_id = ? IF email = 'old@example.com'; -- Insert only if row doesn't exist INSERT INTO users (user_id, username, email) VALUES (?, 'john_doe', 'john@example.com') IF NOT EXISTS; -- Conditional delete DELETE FROM users WHERE user_id = ? IF username = 'deactivated_user';

⚠️ LWT Performance Impact

  • Uses Paxos consensus protocol
  • Requires 4 round trips vs 1 for normal operations
  • Higher latency and lower throughput
  • Use sparingly for critical consistency requirements

⚡ Performance Optimization Strategies

✅ Query Optimization

  • Include Partition Key: Always include partition key in WHERE clause
  • Use Clustering Columns: For range queries and sorting
  • Avoid ALLOW FILTERING: Design tables for your queries
  • Prepared Statements: Use for repeated queries
  • Appropriate Batch Sizes: Keep under 100 statements

❌ Performance Anti-Patterns

  • Full Table Scans: Queries without partition key
  • Large Batches: Over 100 statements in batch
  • Cross-Partition Batches: Batches spanning multiple partitions
  • Secondary Index Overuse: Heavy reliance on secondary indexes
  • Hot Partitions: Uneven data distribution

📊 Key Performance Metrics

Metric Good Range Action If High
Read Latency < 10ms p99 Optimize queries, add caching
Write Latency < 5ms p99 Check disk I/O, tune memtable
Partition Size < 100MB Redesign data model
GC Pause Time < 100ms Tune JVM settings
Compaction Rate Steady progress Increase compaction threads

❓ Interview Preparation

Essential questions and comprehensive answers for Cassandra interviews

💼 Essential Cassandra Interview Questions

Q1: What is Apache Cassandra and what are its key characteristics?
A: Apache Cassandra is a distributed NoSQL database designed for handling large amounts of data across commodity servers with no single point of failure. Key characteristics include: distributed architecture with peer-to-peer communication, wide column store data model, tunable consistency, horizontal scalability, high availability, and eventually consistent data replication.
Q2: Explain Cassandra's ring architecture and how data is distributed.
A: Cassandra uses a ring topology where all nodes are equal peers. Data is distributed using consistent hashing with the Murmur3 partitioner. Each node is responsible for a token range (-2^63 to 2^63-1). Partition keys are hashed to tokens, determining which node stores the data. Virtual nodes (vnodes) improve load distribution and make adding/removing nodes easier.
Q3: What is the difference between partition key and clustering key?
A: Partition key determines which node stores the data and is used for data distribution across the cluster. Clustering key determines the sort order of data within a partition and enables range queries. Together they form the primary key: PRIMARY KEY (partition_key, clustering_key).
Q4: How does Cassandra achieve high availability and fault tolerance?
A: Through data replication across multiple nodes based on replication factor, peer-to-peer architecture with no single point of failure, gossip protocol for failure detection, tunable consistency levels allowing trade-offs between consistency and availability, and automatic data repair mechanisms.
Q5: What are the limitations of CQL compared to SQL?
A: CQL doesn't support: aggregations (sum, avg, count), joins between tables, subqueries, group by/having clauses, wildcard searches, union operations, and complex where clauses without ALLOW FILTERING. These limitations exist because Cassandra is optimized for high-performance reads/writes rather than complex analytical queries.
Q6: Explain the gossip protocol and its role in Cassandra.
A: Gossip protocol is a peer-to-peer communication mechanism where nodes exchange information about cluster state. Each node periodically sends gossip messages containing information about itself and other nodes. This enables failure detection, cluster membership management, and ensures all nodes have consistent view of the cluster topology.
Q7: When would you use Cassandra over other databases?
A: Use Cassandra for: large-scale applications requiring high write throughput, time-series data and IoT applications, applications needing geographic distribution, systems requiring 99.99% uptime, applications with predictable query patterns, and scenarios where eventual consistency is acceptable.
Q8: What is TTL and how is it useful in Cassandra?
A: TTL (Time To Live) automatically expires data after a specified time period. It's useful for managing storage space, removing outdated data automatically, implementing caching mechanisms, and ensuring data freshness. TTL can be set at column or row level and helps maintain optimal database performance.
Q9: How do you model data in Cassandra differently than in RDBMS?
A: Cassandra uses query-first design where you create tables based on specific queries rather than normalized data structures. Key differences include: denormalization for performance, designing one table per query pattern, avoiding joins through data duplication, using composite keys for data organization, and embracing eventual consistency.
Q10: Explain replication strategies in Cassandra.
A: SimpleStrategy: used for single datacenter, places replicas on consecutive nodes in the ring. NetworkTopologyStrategy: used for multiple datacenters, allows specifying replica count per datacenter and considers rack awareness for better fault tolerance. Replication factor determines how many copies of data exist in the cluster.
